# MiniFlow Studio V1: roadmap

**Goal.** Someone who can't code builds, runs, inspects, tests, schedules and fixes a data
workflow in the browser; a developer extends it with new blocks written in Python. In short:
a small, standard-library-only, no-code Airflow.

**Status.** Agreed scope (2026-10-08). Each milestone below gets its own design spec,
implementation plan, tests and demo before the next one starts.

## Research: what the reference tools do best

### Apache NiFi: continuous data movement and traceability
- Data units (FlowFiles) carry content plus attributes; processors route each to a named
  outcome (success, failure), with per-processor retry settings.
- Connections are queues with back-pressure; processors run on timer or cron schedules.
- Data provenance records every event, with lineage views and replay.
- Parameter contexts share settings across a flow; parameters can be sensitive.
- Bulletins show a component's warnings and errors on the component itself.
- Flows are versioned in a registry (Git-backed in 2.0); 2.0 adds Python processors and flow
  analysis rules that lint a flow.

### Apache Hop: pipelines versus workflows, and testing
- Pipelines process data (all transforms run in parallel, streaming rows); workflows
  orchestrate actions in order, following success, failure or unconditional hops.
- Projects and environments let one flow point at dev or production settings.
- After a run, each transform offers a data preview and row metrics (read, written, rejected,
  errors); a failed transform shows its error in place.
- Unit tests replace inputs with data sets and compare outputs with golden data sets.
- `hop-run` runs flows from the command line; Hop Server exposes them as a service.

### KNIME: making building feel safe
- Traffic-light status per node: not configured, configured, executed, error.
- Every output port can be inspected (table preview, statistics, flow variables).
- Partial execution: executing a node runs what it needs; resetting a node resets everything
  downstream.
- Guided building: node search, suggested next nodes, settings side panel, canvas annotations,
  workflow description, and a monitor that jumps to the failing node.
- Components wrap a sub-workflow into a reusable node with its own settings; flow variables
  carry parameters.

## Ideas adopted for V1

| Idea | From | Where in V1 |
|---|---|---|
| Configured blocks with generated settings forms | all | M1 engine, M6 editor |
| Placeholders for data and parameters: `{{ step.x }}`, `{{ params.x }}`, `{{ env.X }}` | NiFi expression language, KNIME flow variables | M1 |
| Parameters, environments (dev/prod), secrets masked everywhere | Hop, NiFi | M1 |
| Flow-level `on_failure` step | Hop failure hops, NiFi failure outcome | M1 |
| Flow checks at load time ("output never used", "secret written in plain text") | NiFi flow analysis rules | M1 |
| Reusable sub-flows with their own settings | KNIME components | M2 |
| Flow tests against expected output | Hop unit tests | M3 |
| Per-step output preview, counts, duration, logs; problem list | KNIME, Hop, NiFi bulletins | M4 |
| Run up to a step, reusing unchanged earlier steps | KNIME partial execution | M5 |
| Traffic lights, palette search, side-panel settings, annotations, templates | KNIME, NiFi | M6 |
| Schedules (interval, daily) | NiFi cron, Airflow | M7 |

## Milestones

| # | Milestone | Needs | Scope |
|---|---|---|---|
| 1 | Engine ✅ | – | JSON flow files; block API with `Setting` types; plugin blocks (`--blocks DIR`); 14 built-in blocks (http_request, read/write CSV and JSON, filter, select, aggregate, sort, shell, sql, email, log, wait); placeholders; parameters, environments, secrets; `on_failure`; non-coder error messages; `miniflow run/validate/graph/blocks` for `.json`; dashboard lists `.json` flows |
| 2 | Sub-flows ✅ | 1 | A JSON flow used as a block inside another flow, with its own settings and outputs |
| 3 | Flow tests ✅ | 1 | `miniflow test`: sample inputs replace chosen steps, outputs compared with expected values |
| 4 | Inspect | 1 | Step output previews (table/JSON), item counts, durations, log messages, problem list |
| 5 | Run up to here | 1, 4 | Run a step and what it needs, reusing earlier steps whose block, settings and inputs are unchanged. **Changes the scheduler's resume interface: agree with the team first (CLAUDE.md).** |
| 6 | Editor | 1–5 | Visual builder in the dashboard: palette, connect, settings panel, traffic lights, annotations, templates, run-to-here, sub-flow editing |
| 7 | Schedules | 1 | `miniflow serve`: interval and daily schedules, shown in the dashboard |

Order: the engine first; sub-flows and tests shape the JSON format, so they come before the
editor is written against it; the editor last among the UI pieces; schedules are independent
and can move earlier.

## Not in V1

Conditional branching and loops, version history in the UI, logins and multiple users,
record-level lineage. Not goals at all: streaming with back-pressure, clusters.

## Constraints

- The core package stays standard-library only (spec §3.1); every block is built on the
  standard library.
- `scheduler.py`, `store.py`, `executors.py` and `graph.py` interfaces change only where a
  milestone says so, after the team agrees.
- Every milestone: tests first, ruff, mypy strict, coverage ≥ 90 %, CI green on Ubuntu and
  Windows, a short browser or CLI demo.
