# Evaluation: findings

This is the interpretation of the measurements in [results/results.md](results/results.md),
which is generated by `uv run python -m benchmarks.run`. The numbers below are from that file,
measured on the development laptop: Intel Core i5-1135G7 with 4 physical cores and 8 logical
CPUs, Windows 11, Python 3.13.6, 8 workers, median of 3 runs. They are written to be adapted
into the report's results section. Laptop turbo and thermal behaviour move individual wall
times by about ±20 % between sessions. The conclusions below held in every session.

## 1. Speedup on synthetic DAGs (spec §3.8, first bullet)

- **io-bound tasks reach the best possible schedule.** On fan-out, diamond and layered graphs
  MiniFlow achieves ×5.55, ×4.03 and ×7.77, which is 97-98 % of the best possible speedup for
  each shape (×5.67, ×4.11, ×8). On the chain it is ×0.99: no parallelism exists, and the
  scheduler costs about 1 %. These match Dask's threaded scheduler to within 2 %.
- **The simple bounds are loose; the shape matters.** For the 34-task fan-out, min(P, work/span)
  allows ×8, but the 32 middle tasks need ceil(32 / 8) = 4 waves on 8 workers. The best
  schedule is therefore 6 task-lengths long, so ×34/6 = ×5.67 is the true ceiling. This is
  Graham's list-scheduling picture [4]. The Amdahl view (serial fraction = depth / tasks)
  *under*-estimates fan-out (×4.95) because it assumes perfectly divisible work.
- **cpu-bound tasks are limited by physical cores and process overhead.** Pure-Python
  arithmetic holds the GIL and does not benefit from hyperthreads, so the ceiling is 4 cores,
  not 8 workers (×3.4, ×2.85 and ×4 for the three shapes). MiniFlow reaches ×2.35-2.94, which
  is 69-84 % of that ceiling. The rest goes to spawning work onto other processes (pickling
  each task and result) and to the laptop's turbo dropping when all four cores are busy. The
  sequential baseline runs on one core at full turbo.
- **Against Dask on cpu work:** Dask's multiprocessing scheduler matches MiniFlow on the flat
  fan-out (×2.58 vs ×2.35) but falls to ×1.08-1.09 on the diamond and layered graphs, where
  MiniFlow keeps ×2.4-2.9. Dask's local multiprocessing scheduler moves every intermediate
  result back to the parent process between dependent steps. MiniFlow does too, but releases
  each task the moment its inputs exist, so deep graphs keep all cores busy. Dask's
  `distributed` scheduler was not tested and may behave differently.

## 2. Choosing the worker per task (second bullet)

One workload: 32 io tasks (0.2 s waits) and 8 cpu tasks (0.2 s compute) in parallel.

| configuration | wall time | speedup |
|---|---|---|
| everything on threads | 1.41 s | ×5.6 |
| everything on processes | 1.31 s | ×6.1 |
| **MiniFlow routing (io → threads, cpu → processes)** | **0.84 s** | **×9.5** |

On threads, the 8 cpu tasks serialise on the GIL. On processes, the 32 waits queue behind
a pool sized to the core count. Routing each task to the worker that suits it is 1.6-1.7×
faster than either uniform choice. This is the central claim of the project (§2.7).

## 3. Scheduler overhead (third bullet)

Time per *empty* task in random layered graphs of up to 5,000 tasks:

- **In-memory store: about 120 µs per task** once the graph has a few hundred tasks. It stays
  flat up to 5,000 tasks, so the per-task cost doesn't grow with graph size. Small graphs cost
  more per task (383 µs at 10 tasks) because pool start-up and run bookkeeping are shared
  among few tasks.
- **SQLite file store: about 360 µs per task.** The extra ~240 µs is the price of durability:
  every state change is a committed transaction, which is what makes `resume` possible after
  a crash.
- **Dask (threaded): 68-88 µs per task.** Dask is roughly 1.5-1.8× cheaper per task. Unlike
  MiniFlow, it records nothing per task, has no retry or state machine, and keeps no history.
- In practice the overhead is negligible for tasks of more than a few milliseconds. At 120 µs
  per task, a 50 ms task loses 0.24 % to scheduling.

## 4. Fault tolerance (fourth bullet)

A 30-task layered DAG where every attempt fails independently with probability p, with 20
runs per point:

- **Measured success rates follow the analytical model** P(run ok) = (1 − p^(r+1))^30 for r
  retries (see `e4_fault_success.png`). With no retries, even p = 0.05 sinks most runs
  (15 % succeed vs 21 % expected). With 3 retries, runs survive p = 0.2 in 100 % of cases
  (95 % expected) and p = 0.3 in 90 % (78 % expected).
- **The cost is predictable.** Mean attempts per task that ran equal 1 + p + … + p^r. At
  p = 0.5 that is 1.5 for one retry (measured 1.49) and 1.875 for three (measured 1.91).
- **Failures never hang a run.** Every run ended, permanent failures marked their descendants
  SKIPPED, and every FAILED task used exactly retries + 1 attempts (checked by the harness).

## 5. Correctness (fifth bullet)

Every MiniFlow run in the experiments was checked automatically against the state store:
**440 runs, 63,083 attempts, 0 violations.** For every attempt, all upstream tasks had
finished before it started, using the timestamps recorded inside the workers. Every
SKIPPED task had a FAILED ancestor. Every FAILED task used exactly its retry budget. In the
test suite, 15 randomly generated DAGs (hypothesis) are checked the same way on every CI run.

## Threats to validity

- One machine, a laptop with turbo. cpu-bound results depend heavily on core count and
  thermal limits. A desktop or server would show higher cpu speedups.
- Synthetic tasks have equal costs. Real pipelines have skewed costs, where critical-path
  priority matters more; this effect was not measured separately.
- Dask comparisons use its local schedulers (`dask.threaded`, `dask.multiprocessing`), not
  `dask.distributed`.
- Timeout behaviour for threads and processes is "fail and abandon" (Python cannot
  interrupt them). It is covered by tests, not by these benchmarks.
